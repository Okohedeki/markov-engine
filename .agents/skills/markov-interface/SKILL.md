# Markov Interface Principles

Markov begins when a person encounters something interesting and ends when that source becomes understanding, a new connection, or finished work.

The product belief is:

> A source is not the answer. It is the first node.

The customer-facing progression is:

```text
Encounter
→ Understand
→ Verify
→ Connect
→ Discover
→ Finish
```

## What Markov sells

Markov is the layer between encountering information and using it.

The user can start with:

- YouTube.
- TikTok.
- Articles.
- PDFs.
- Audio or podcasts.
- Social posts.
- A plain question.

The user can leave with:

- **Catch me up** — the substance, missing context, questionable claims, and threads worth following.
- **Explore where it leads** — evidence, hidden relationships, hypotheses, and a larger story.
- **Turn it into a script** — a defensible original angle and a finished factual script.

These are user jobs, not three unrelated product modules.

## Public-page priorities

The first viewport should make the core behavior obvious:

1. Paste a link, upload a source, or ask a question.
2. See the supported source types.
3. Understand that Markov goes beyond the submitted source.
4. See a real source-to-insight transformation.
5. Choose the next job.
6. Understand that local use is free and open source.

Do not lead with the API, agent infrastructure, evidence schema, or internal research terminology.

## Product-specific proof

The best Markov proof is a single realistic transformation:

```text
Starting source
→ important claim
→ missing assumption
→ hidden intermediary or connection
→ evidence and disagreement
→ new angle
→ finished output
```

Use real or clearly labeled sample material. Preserve exact source links, timestamps, pages, and uncertainty when shown.

Never use fictional evidence quotations, invented case IDs, fake claim IDs, fabricated usage counts, fake customer logos, or a decorative dashboard that does not demonstrate Markov's job.

## Connection design

Connections are not a generic node graph.

Prefer readable forms such as:

- Causal paths.
- Branching annotations.
- Timelines.
- Before-and-after explanations.
- “What connects these?” cards.
- Evidence-backed hypothesis trails.
- Side-by-side source comparisons.

Every connection shown to the user should communicate:

- What is connected.
- The mechanism.
- Why it matters.
- What supports it.
- Where it may break.
- Whether it is established, interpreted, hypothetical, or speculative.

Do not use network visualization merely because Markov has graph data.

## Language

Use plain verbs:

- Paste.
- Read.
- Catch up.
- Follow.
- Compare.
- Check.
- Explore.
- Turn into a script.

Avoid public-facing phrases such as:

- AI-powered.
- Agentic.
- Multimodal ingestion.
- Evidence desk.
- Research infrastructure.
- Knowledge graph.
- Claim object.
- Artifact renderer.
- Case orchestration.

Those may appear in developer documentation when technically necessary.

## Visual character

Markov should feel like an instrument for curiosity and thinking, not a generic SaaS dashboard or an academic compliance tool.

Derive the visual direction from:

- Sources arriving in different forms.
- An idea branching into paths.
- Annotations revealing what was omitted.
- Evidence staying attached to an emerging insight.
- A finished artifact growing from the same research trail.

Do not prescribe one permanent aesthetic. The implementation may be quiet, playful, editorial, utilitarian, or experimental if it makes these behaviors clearer. Avoid costumes that imply rigor without demonstrating it.

## Application UX

The intake should begin with one universal action and reveal complexity progressively.

After input, let the user choose:

```text
Catch me up
Explore where it leads
Turn it into a script
```

Show processing in human terms:

```text
Reading the source
Finding the important claims
Filling in missing context
Checking the evidence
Following promising connections
Building the output
```

Results should lead with the finished answer or artifact. Claims, evidence, sources, and connection trails are supporting layers, not the first thing every user must decode.

## Free and open-source behavior

Public pages must distinguish truthfully between:

- **Run locally** — free, open source, user's hardware, models, keys, and storage.
- **Hosted Markov** — only claim this when a working hosted experience exists.

Do not call GitHub installation instructions “Open Markov” or “Try Markov.”

## Markov self-check

Before shipping a Markov interface, ask:

- Is the universal input visible and understandable?
- Does the design show that the source is a beginning rather than an endpoint?
- Is at least one hidden connection demonstrated concretely?
- Can the user see what finished work comes out?
- Are evidence and uncertainty truthful?
- Does the page feel like Markov after removing the logo?
